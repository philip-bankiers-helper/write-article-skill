# HTML Lane: the Slate Style

Every rule here was learned by doing it wrong first. The original six Triton/TLX diagrams were rejected whole ("not polished enough, doesn't add enough info, don't feel like they add a lot of value") and redesigned from scratch; the redesigns passed first review. This file is what the redesigns knew.

## When this lane fires

The diagram carries verbatim technical text beyond short labels: code, IR, instruction names, exact latency numbers, file paths, tables of figures. Text like that must be pixel-exact, so it's authored as HTML and rendered — never generated by a raster model.

## Slate

The house style, self-contained. No other article's diagrams needed as reference.

- Background `#0a0c10`. Dark theme, always.
- Accent semantics — the color means the same thing in every diagram of every article:
  - blue `#60a5fa` — memory, data movement
  - amber `#fbbf24` — synchronization, barriers
  - purple `#c084fc` — compute, MMA
  - green `#4ade80` — control, speculation
- Supporting defaults (tunable, keep the feel): body text `#e2e8f0`, muted text `#94a3b8`, panel fill `#111827`, hairline borders `#1f2937`.
- Type: system sans for labels; monospace (`ui-monospace`, `SF Mono`, `Menlo`) for anything code. Monospace minimum 12px, 13px preferred. If you have to squint, the diagram has failed.

## Principles

**One clear insight.** Before building, write the one question the diagram answers, in one sentence. Can't? The diagram is confused.

**Real content, not labels.** Actual IR snippets, real latency numbers ("~700 cycles"), real PTX instructions, real file paths. Generic colored boxes with category names don't earn a place in the article. Ask: does this teach the reader something they couldn't get from the prose?

**Readability over density.** Cramming is the single most common failure.

**2×2 card grids over wide tables.** A table with 4+ columns of small monospace is unreadable at render size; a card grid with large text and clear separation isn't. (The Triton translation table took three full redesigns to learn this.)

**Two-column layouts for flows.** Definition on the left, runtime sequence on the right. Cause-effect becomes spatial. Works for anything with a "recipe" and a "runtime behavior."

**Real numbers in memory-hierarchy diagrams.** "HBM ~700 cycles, L2 ~200 cycles, SMEM ~20 cycles, registers 1 cycle" is worth more than colored tiers.

## Authoring requirements

- One standalone `.html` file per diagram. No external fonts, no CDNs — the render must be deterministic offline.
- Fixed canvas: `body { width: 860px; margin: 0; }` plus an explicit pixel height. You author the height; the render command needs it.
- 860px is the bound. Fits article columns and previews. Don't go wider.

## Render and read back

```
${CLAUDE_SKILL_DIR}/scripts/render-html.sh assets/01-<name>.html assets/01-<name>.png 860 <height>
```

Renders at 2× device scale (a 1720px-wide PNG) through headless Chrome. Then **read the PNG file** — not the HTML — and check:

- nothing clipped at any edge
- every string readable without zooming
- no overlapping elements
- the one-question insight is actually visible
- accent colors match their semantics

Budget 2–3 passes minimum. First pass establishes structure. Second balances density and readability. Third fixes the thing you couldn't see until the render.

## Preflight

Before writing any diagram HTML, answer: (1) what is the one question this answers? (2) what real code or numbers will it show? (3) will the text be readable at 860px? If you can't answer all three, rethink the diagram.
